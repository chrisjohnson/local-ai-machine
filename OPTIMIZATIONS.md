## Qwen3.6-35B-A3B real benchmark data — kyuz0 toolboxes site (verified 2026-07-22)

Source: `https://kyuz0.github.io/amd-strix-halo-toolboxes/`, underlying data pulled directly from `https://kyuz0.github.io/amd-strix-halo-toolboxes/results.json` (the page renders this JSON client-side; WebFetch alone only sees the empty page shell, so the raw JSON was fetched directly to get real numbers). This is real, machine-generated benchmark data (not an LLM's guess), run on a Framework Desktop / Ryzen AI MAX 395+ / 128GB unified RAM — same chip family as this machine (gfx1151) — via `llama.cpp`. Data generated 2026-05-18, on Fedora Linux 43, kernel 6.19.12.

**Answering the question "could 35B-A3B at 16-bit quant hit 300+ tok/sec?" — no, not for text generation.** The actual `Qwen3.6-35B-A3B-BF16` results (30 runs across 5 backend environments: `rocm-7_2_3`, `rocm6_4_4`, `rocm7-nightlies`, `vulkan_amdvlk`, `vulkan_radv`, all with flash attention on, `ngl=99`):

- **Text generation (tg128, default/short context)**: best result was **26.01 tok/s** (ROCm 7.2.3). ROCm 6.4.4 and ROCm 7-nightlies were close behind (~25-26 tok/s). Vulkan backends were much slower for TG: RADV 10.68 tok/s, AMDVLK 11.6 tok/s.
- **Prompt processing (pp512, default context)**: this is where large numbers show up — ROCm 6.4.4 hit **573.71 tok/s**, ROCm 7.2.3 hit 525.94, ROCm 7-nightlies 528.97 tok/s. Vulkan RADV hit 328.4 tok/s, AMDVLK only 122.89 tok/s. **So the "300+ tok/s" figure is real, but it's a prompt-processing (prefill) number, not a generation (decode) speed** — likely what's being misread on the page.
- Longer contexts degrade both PP and TG somewhat (e.g. BF16 ROCm 7.2.3: pp2048@32k context = 417.86 tok/s, pp2048@65k context = 322.65 tok/s; tg32@32k = 23.91 tok/s, tg32@65k = 22.2 tok/s).

For comparison, quantized variants of the same model (also in the dataset) generate much faster than BF16:
- **Q4_K_XL**: tg128 best = **60.43 tok/s** (Vulkan RADV) / ~51 tok/s (ROCm). pp512 best = 1120 tok/s (ROCm 7.2.3).
- **Q8_K_XL**: tg128 best = **46.53 tok/s** (Vulkan AMDVLK) / ~46 tok/s (ROCm). pp512 best = ~1095 tok/s (ROCm).

**Takeaway for this machine**: BF16 (full 16-bit) is the slowest option for actual token generation (~26 tok/s ceiling) despite having the fastest-looking prompt-processing numbers on the page — the 300+ figures on that page are PP throughput, not TG/decode throughput, and pp512 is a burst/short-prompt metric, not sustained output speed. If generation speed for interactive/agentic use is the priority, the quantized (Q4_K_XL or Q8_K_XL) variants roughly double-to-triple TG speed vs BF16 on this hardware class. Also notable: ROCm environments substantially beat Vulkan for prompt processing on BF16, but Vulkan RADV actually wins on TG for the quantized variants — backend choice matters and isn't uniformly "ROCm always wins."

## Lemonade Server & Ollama — verified against official sources (2026-07-24), corrects the Reddit-based speculation above

The Reddit-thread research above was explicitly flagged as low-confidence (single unverified OP post, OS/Docker environment never stated). Re-researched directly against official docs/repos before any setup work, per Phase 5.6.

**Lemonade Server — Hybrid Mode (the entire reason it was on the list) is Windows-only, full stop.** Confirmed via the project's own FAQ (`github.com/lemonade-sdk/lemonade/blob/main/docs/guide/faq.md`), verbatim: *"Ryzen AI SW's implementation of NPU and hybrid inference is currently supported only on Windows."* Linux and Docker are both genuinely supported (official image `ghcr.io/lemonade-sdk/lemonade-server:latest`, official install docs for Ubuntu/Debian/Fedora/Arch, OpenAI-compatible API at `/v1`) — but on Linux, Lemonade's own GPU story for this chip is just "use the experimental `vllm:rocm` backend," i.e., the same vLLM we already run. **Conclusion: not worth pursuing.** It would not touch the idle NPU on this machine's actual OS — it would just be a second OpenAI-compatible server duplicating vLLM's existing GPU-only path. The NPU-idle problem remains genuinely unsolved on Linux as of this check; no known tool here changes that today.

**Ollama — mechanically straightforward, but gfx1151-on-Linux has two open, unresolved upstream regressions worth taking seriously.** Official image `ollama/ollama:rocm`, same `--device /dev/kfd --device /dev/dri` + video/render group pattern as the existing vLLM containers, OpenAI-compatible API confirmed (`/v1/chat/completions`), gfx1151 officially listed as supported hardware (`docs.ollama.com/gpu`). - `ollama/ollama#13589` (open): gfx1151 (Radeon 8060S/8050S) silently falls back to CPU on Linux despite `rocminfo` correctly detecting the GPU — confirmed working on Windows, broken on Linux, unresolved.

**Implication for any Ollama benchmark data gathered on this machine**: silent CPU fallback is the specific, real, twice-reported failure mode on this exact chip — any speed numbers gathered must be validated against actual GPU utilization (e.g. `node_amdgpu_busy_percent` via the Grafana dashboard, or `amdgpu_top`) at the time of the benchmark, not just trusted because the container started and returned tokens. ## Second deep-dive pass (2026-07-24): FastFlowLM (real NPU answer) and confirmed-working MTP

Requested explicitly to check whether the first two research passes (model candidates; Lemonade/Ollama) were genuinely thorough rather than a shallow first hit. This pass found two significant, previously-missed leads.

**FastFlowLM — a real, current, Linux-native answer to the idle-NPU problem, independent of Lemonade.** Actively maintained (`github.com/FastFlowLM/FastFlowLM`), explicitly lists Strix Halo as supported, added native Linux support March 2026, and AMD itself announced integration with it in July 2026 — this is not a hobby project. Runs LLM inference **entirely on the NPU** (no GPU/CPU load), Ollama-like CLI/API. Real requirements/caveats: Linux kernel 7.0+ (or the `amdxdna-dkms` backport), NPU firmware ≥1.1.0.0, and **AMD IOMMU must be enabled** — worth noting IOMMU is sometimes disabled specifically to maximize iGPU throughput on Strix Halo boxes, so enabling it for NPU use may cost a small amount of iGPU performance (one community report: +3.29% latency on a concurrent 64K iGPU workload — a real tradeoff to weigh, not free). A known Ubuntu 25.10 firmware/driver mismatch bug is open upstream (`amd/xdna-driver#1219`) — worth checking against this machine's actual NixOS kernel/firmware pairing before attempting setup, not assuming it'll just work. AMD's own Ryzen AI Software / ONNX Runtime GenAI (OGA) stack exists independently of Lemonade too, but is fundamentally Windows/ONNX-first with no clean native-Linux path found — FastFlowLM is the one credible current answer.

**MTP speculative decoding is confirmed working today — via llama.cpp, not vLLM.** llama.cpp merged native MTP support (`ggml-org/llama.cpp` PR #22673, merged 2026-05-16) for models shipping MTP heads, including Qwen3.6-27B and Qwen3.6-35B-A3B — both already in this machine's lineup. Real caveats: `n_parallel=1` only (no concurrent request serving while using MTP), and ROCm+tensor-parallel combinations reportedly crash — Vulkan is the safer backend for this specifically. **No vLLM MTP evidence on this hardware was found** — vLLM's `qwen3_next_mtp` path remains unconfirmed on ROCm, consistent with the existing roadmap note; MTP being "real" is specific to the llama.cpp path, not a green light for vLLM.

## Fourth pass (2026-07-24): llama-server concurrent-serving gap, Ollama version re-verification, new MoE model survey

Three research leads, each independently verified via direct tool calls (docker on the actual remote box over SSH, GitHub API, HuggingFace API) — not a cold query. Every claim below traces to a real, checkable source; nothing here is repeated from a model's memory without verification.

### Lead 1: llama-server concurrent/parallel serving — real gap confirmed, plus a serious real bug just found on this exact chip

**The toolbox image does bundle `llama-server`, confirmed directly on the actual machine** (not a local Mac docker pull, which would test the wrong architecture): `ssh chris@local-ai-machine.local "docker run --rm kyuz0/amd-strix-halo-toolboxes:vulkan-radv which llama-server"` → `/usr/bin/llama-server`, same build as the existing benchmarks (version 10107, `c0bc8591e`).

**Real, confirmed flags for concurrent serving** (from the binary's own `--help`, not assumed):
- `-np, --parallel N` — number of server slots (default `-1` = auto). This is the flag that turns on multi-client continuous batching.
- `-cb, --cont-batching` — continuous/dynamic batching, **enabled by default**.
- `-kvu, --kv-unified` — single unified KV buffer shared across all sequences (default: enabled when slots is auto). This is the flag implicated in the bug below.
- `--cache-idle-slots` — saves idle slots to the prompt cache (default enabled, requires `--cache-ram`).
- `--slots` / `--no-slots` — exposes a `/slots` monitoring endpoint (default: enabled) — useful for observing real concurrent-slot behavior during a future benchmark.

**No existing benchmark data for `llama-server` multi-client throughput exists anywhere checked** — confirmed by directly parsing kyuz0's raw `results.json` (554 runs): every single run's `test` field is one of `pp512`, `tg128`, `pp2048 @ d32768/d65536`, `tg32 @ d32768/d65536` — all `llama-bench` single-stream metrics, no `n_parallel`/concurrency field exists in the schema at all. Cross-checked kyuz0's own `benchmark/run_benchmarks.sh` directly (fetched from GitHub) — it invokes only `llama-bench`, never `llama-server`. The toolbox's own README example invocations also stick to `--parallel 1` even in its documented "router mode" (`llama-server --models-preset models.ini ... --parallel 1`). **This is a genuine, confirmed gap** — no one (including kyuz0) has published `llama-server` concurrent-serving numbers for gfx1151 anywhere found.

**More important finding, not in the original ask but directly relevant and time-sensitive: a real, currently-open, actively-being-fixed data-corruption bug affects exactly this scenario on exactly this chip.** `ggml-org/llama.cpp#25992` ("server -np 4 --kv-unified returns other requests' responses verbatim on integrated HIP GPU (gfx1151)"), opened 2026-07-22, last updated 2026-07-24 (today/yesterday relative to this research). Under concurrent mixed load (`-np 4 --kv-unified`) on an **HIP/ROCm** backend integrated GPU, `llama-server` returns complete responses that verbatim belong to a *different, earlier request* — bisected to a specific commit (`c7d87229`, "restore prop.integrated on HIP builds", merged via PR #24233) that re-enabled a direct ROCm-host compute path previously disabled for exactly this corruption class. Confirmed by four independent reporters, all on this same chip family:
- OP: AMD Ryzen AI Max+ 395, gfx1151, 128GB UMA, ROCm 7.14 — reproduces deterministically within 2-4 rounds of a scripted nonce-echo test.
- `imrehg`: AMD Radeon 890M (gfx1150, Strix Point sibling), 96GB — same bug, also reports it on `--parallel 1`/`--no-kv-unified` in some cases, not purely a multi-slot issue.
- `herczy`: GMKtec EVO-X2 (same Ryzen AI Max+ 395/Radeon 8060S/128GB as our exact box), ROCm 7.2.4 and 7.14 both fail — garbled output on MiniMax M2.7, wrong-tool-call hallucination on Qwen models (would directly break agentic tool-calling workflows).
- `ascotai`: explicitly reports this breaking **Qwen tool calling from VS Code/agents** and "a Hermes agent go haywire" — directly relevant to this project's own agent-orchestration use case.

**Critical mitigating fact for us: every one of these reporters confirms switching to the Vulkan backend fixes it** (`imrehg`: "Switching to `--device Vulkan0` ... mitigates the error"; `herczy`: "I also switched over to a Vulkan-based build and it fixed all issues"; `ascotai`: "I also was using Vulkan in the meantime without issues"). **Our toolbox image is `kyuz0/amd-strix-halo-toolboxes:vulkan-radv` — the Vulkan/RADV backend, not HIP/ROCm** — so this specific bug, as characterized by the bisect, should not affect us directly. A fix PR (`ggml-org/llama.cpp#25863`, "avoid direct ROCm_Host compute on HIP integrated GPUs") is open and awaiting review as of 2026-07-24, with an AMD engineer (`liminfei-amd`) engaged on the issue thread.

**A second, separate, gfx1151/RADV-Vulkan-specific concurrency bug was also found, but it's old, unresolved, and was auto-closed for staleness — not a clean bill of health.** `ggml-org/llama.cpp#20906` ("Slot gets stuck after batch processing... when 2 requests running concurrently"), filed directly against `RADV GFX1151` (our exact backend) via the `kyuz0/amd-strix-halo-vllm-toolboxes` distro, describing slot 0 hanging indefinitely after prompt processing under 2 concurrent requests. **This issue was never actually fixed** — GitHub's bot auto-closed it "because it has been inactive for 14 days since being marked as stale" (2026-05-07), not because anyone confirmed a resolution. A related bot-linked issue (`#20890`, "Vulkan regression - same Vulkan backend with AMD GPU (RADV)") suggests this class of Vulkan-parallel-slot bug has recurred before. **Honest conclusion: a real `llama-server --parallel N` benchmark attempt on this hardware should specifically watch for stuck/hung slots under concurrent load, not just assume Vulkan is automatically safe** — it dodges the HIP-specific corruption bug (#25992) but has its own unresolved (if stale/abandoned) history of concurrency issues on the exact same backend.

**Net assessment**: Lead 1 is real and actionable — `llama-server --parallel N --cont-batching` is a genuine, previously untested capability on this exact toolbox image, and would close a real gap in the current benchmark set (a true c1/c8-style llama.cpp comparison against vLLM). But it should not be treated as a routine benchmark to just run — go in expecting to specifically validate output correctness (not just throughput) under concurrency, given the HIP corruption bug (dodged by our Vulkan build, but recent and still being patched) and the older, unresolved Vulkan slot-hang report on this identical backend/hardware combination. This is exactly the kind of finding that argues for correctness-checking (e.g., an adapted version of the nonce/replay-detection script from issue #25992) alongside any throughput measurement, not blind trust in tok/s numbers.

### Lead 2: Ollama version tradeoff — largely stale, current best answer is much more nuanced than "0.17.7 vs 0.18.x+"

The existing pin (`ollama/ollama:0.17.7`, chosen for a Vulkan-libs fix) and the "0.18.x+ reintroduces a GPU-detection regression" belief were checked directly against current GitHub state. **Ollama has moved far past that range**: latest stable release as of this check is **v0.32.3** (published 2026-07-23, i.e. yesterday relative to this research pass) — 0.17.7/0.18.x is now roughly 15 minor versions and several months stale.

**Both specific issues cited in our existing research were re-checked directly, comment-by-comment, not just for open/closed status:**

- **`ollama/ollama#13589`** (gfx1151 silently falls back to CPU) — closed, `state_reason: completed`. Real root cause (confirmed via the thread's own debugging): a `rocBLAS` GPU-kernel VM-fault on gfx1151 that a `HSA_OVERRIDE_GFX_VERSION` override does not fix. **The actual fix landed in Ollama 0.17.8**, which bundles ROCm 7 — a maintainer (`dhiltgen`) posted this directly in the thread on 2026-03-11. A separate user (`Znuff`) later confirmed real ROCm GPU detection working as of **2026-04-17** on Ollama 0.18.3, specifically once paired with a Linux kernel ≥6.17.0-19.19~24.04.2 (Ubuntu HWE) and a matching amdgpu userspace driver (~31.10 from `repo.radeon.com`, not the default packaged 30.30.x) — AMD's own docs recommend kernel ≥6.18.4 for Strix Halo. **This directly contradicts the "0.18.x+ broke it" belief** — 0.18.x fixed it, conditioned on the host OS/kernel/driver stack actually meeting the newer requirements, which many reporters' systems didn't at the time.
- **`ollama/ollama#15336`** ("0.17.7 last version working, 0.18.x fallback to CPU") — closed, `state_reason: completed`. The reporter's own final comment (2026-04-05) is the resolution: their real root cause was an **old kernel** (6.14.0-37-generic), not the Ollama version — upgrading to **6.17.0-20-generic** fixed GPU detection cleanly on **Ollama 0.20.2**, and they explicitly confirmed it **"working perfectly with 0.20.2 and gemma4"** — i.e., both the GPU-detection issue and the `gemma4` architecture-support gap this project hit on 0.17.7 are resolved together on a sufunknown-but-modern release, given a modern-enough kernel.
- **This machine's actual kernel is 6.18.39** (checked directly via `ssh chris@local-ai-machine.local uname -r`) — comfortably clears every version bar mentioned above (AMD's own ≥6.18.4 recommendation, and the ≥6.17.0-20 threshold that fixed #15336 for its reporter). Being NixOS rather than Ubuntu, the specific "need amdgpu userspace driver ~31.10 from repo.radeon.com" caveat from the #13589 thread is very likely moot here — NixOS's amdgpu driver comes bundled with the kernel package itself, not a separately-versioned Ubuntu/AMD repo package, and our kernel already exceeds every version threshold discussed in that thread.
- **`gemma4` architecture support**: confirmed directly from Ollama's own release changelogs (not assumed) — `gemma4` support, including the exact `26b-a4b-it` variant already downloaded on this machine, has been present since **v0.21.0** (2026-04-16, "Gemma 4 on MLX... Added support for running Gemma 4 via MLX on Apple Silicon"), with subsequent releases adding QAT weights (`gemma4:26b-a4b-it-qat`, v0.30.6), MTP speculative decoding for Gemma 4 (v0.23.1, Mac-only), and tool-calling/reasoning improvements (v0.32.1). **The specific `unknown model architecture: 'gemma4'` failure this project hit on 0.17.7 would not reproduce on any Ollama release from the last ~3+ months.**

**A different, real, currently-open regression was found instead — and it's more relevant to us than the stale 0.17.7-vs-0.18.x framing.** `ollama/ollama#16462`, "AMD Strix Halo VRAM Detection Regression in Ollama 0.30+ (Container Deployment)", opened 2026-06-03, **still open and actively commented on as recently as 2026-07-22** (two days before this research). Root cause (confirmed via 28 comments of real debugging, including from an Ollama maintainer `dhiltgen`): starting at Ollama 0.30.0, the **ROCm backend specifically** under-reports available memory on Strix Halo — `ggml_backend_cuda_get_available_uma_memory()` (used by the ROCm/HIP path) reads `/proc/meminfo`'s `MemAvailable` rather than the actual GTT/VRAM carveout, capping usable memory at roughly free system RAM instead of the real ~100GB+ pool, so large models spill to CPU or fail to load. **Confirmed real, current, and unresolved**: an Ollama maintainer (`dhiltgen`, 2026-07-01) links it to a still-open upstream llama.cpp issue (`ggml-org/llama.cpp#18159`, opened 2025-12-18, confirmed still open as of 2026-07-14) rather than an Ollama-side fix, and a user as recently as 2026-07-17 reports being "stuck on version 0.24 for more than 2 months" waiting on it. **The confirmed, repeatedly-corroborated workaround (multiple independent reporters, including one posting a direct before/after benchmark) is to run the Vulkan image instead of the `-rocm` tag** (`ollama/ollama:latest`, non-`-rocm`) **plus `OLLAMA_IGPU_ENABLE=1`** — one reporter's own numbers: broken ROCm path capped at "27.9 GiB available" causing GPT-OSS-120B to spill to CPU (2.5 tok/s), Vulkan + the flag correctly detected "111.1 GiB available" and ran the same model at 37.5 tok/s, 100% GPU. This is consistent with, and reinforces, this project's own already-established finding that Vulkan/RADV tends to beat ROCm for token generation on this exact chip.

**Revised bottom line for lead 2**: the original "pin to 0.17.7 or risk 0.18.x+ regression" framing is stale and, per the actual issue threads, was never really an Ollama-version story so much as a host-kernel-version story — both cited bugs trace back to reporters' Linux kernels being too old, not to the Ollama release itself. This machine's kernel (6.18.39) already clears every bar mentioned in those threads. **A real, currently-open, and more relevant regression exists in the 0.30+ line** (VRAM-detection undercounting on the ROCm backend specifically, container-deployment-affecting, unresolved upstream as of 2026-07-14) — but it has a clean, well-corroborated workaround (use the Vulkan/non-`-rocm` image + `OLLAMA_IGPU_ENABLE=1`), which also sidesteps the separate HIP-integrated-GPU corruption bug found in lead 1. **Recommendation, not yet acted on**: if/when Ollama is revisited, a modern release (e.g. current v0.32.3) via the **Vulkan image tag + `OLLAMA_IGPU_ENABLE=1`** (not the `-rocm` tag) is very likely both the correctness-safe and the `gemma4`-capable choice — a meaningfully different, and better-supported, recommendation than the original 0.17.7 pin. Not implemented as part of this research pass (no download/config change made) — flagged for the next time Ollama is actually re-benchmarked.

Searched HuggingFace's API directly (not a cold-recall list) across Qwen, Google/Gemma, Z.AI/GLM, DeepSeek, Mistral, MiniMax, and Moonshot/Kimi for anything in the same ~30B-total/~3B-active shape (or a comparably favorable active-fraction) as the models already winning here (Gemma-4-26B-A4B, Qwen3.6-35B-A3B, GLM-4.7-Flash).
