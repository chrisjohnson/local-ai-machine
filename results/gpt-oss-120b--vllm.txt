*** METHODOLOGY DEVIATION, real and necessary, not optional ***
GPT-OSS's chat template uses OpenAI's "harmony" response format (special channel/message
control tokens parsed by vllm's built-in harmony parser, wired in via
--tool-call-parser openai --reasoning-parser openai_gptoss). The project's standard
`vllm bench serve --backend openai-chat --endpoint /v1/chat/completions --ignore-eos` recipe
is INCOMPATIBLE with this model: --ignore-eos forces the sampler to keep generating past the
model's natural end-of-turn token, and continued generation past that point violates harmony's
expected token grammar, causing every request to error out server-side with:
  openai_harmony.HarmonyError: Unexpected token 200002 while expecting start token 200006
Confirmed independently via a manual curl to /v1/chat/completions with "ignore_eos": true --
reproduced 100% of the time. A normal chat request (no ignore_eos) works fine and returns
finish_reason: length cleanly when max_tokens is hit -- the harmony parser only breaks under
forced continued generation past the natural stop point, not under simple truncation.
FIX USED: switched `vllm bench serve` to `--backend openai --endpoint /v1/completions`
(the raw-completions endpoint, bypassing the chat template / harmony parser entirely).
Confirmed via manual curl to /v1/completions with ignore_eos:true -- works cleanly, no error.
This is the same --ignore-eos/--random-input-len/--random-output-len/--num-prompts convention
as every other model in this project, just a different backend/endpoint pair to route around
this model-family-specific incompatibility. Flagging this explicitly per BENCHMARKING.md's
honesty rule -- this is a genuine methodology change for this model family, not a silent
substitution.

Notes: c1 throughput (8.46 tok/s) is notably slow for a ~5.1B-active-param MoE model on this
hardware -- slower even than the dense Qwen3.6-27B (4.07 tok/s c1... actually faster than that,
but far behind the other small-active-param MoE models: Qwen3.6-35B-A3B 11.91 tok/s c1,
Gemma-4-26B-A4B-it 20.85 tok/s c1, GLM-4.7-Flash-AWQ 18.95 tok/s c1). Likely cause (not fully
isolated): MXFP4 is a very new quant format and this hardware (gfx1151/RDNA3.5) has no native
FP4 matrix-core support (same reason bf16 was chosen over FP8 for the primary) -- the
"Using MoEPrepareAndFinalizeNoDPEPMonolithic" log line suggests a non-optimized MXFP4 MoE
kernel path on this toolbox build, plausibly dequantizing to a compute-friendly format on the
fly rather than running true low-bit matmuls, which would explain the gap versus the other
MoE models' higher-bandwidth-native quant formats (bf16, AWQ-4bit). Not confirmed via kernel
profiling -- a real, measured result, but the "why" is a plausible hypothesis, not a verified
root cause.
