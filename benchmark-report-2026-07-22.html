All runs: vllm bench serve, random dataset, --ignore-eos (fixed output length for clean throughput comparison), 20-32 prompts per run. Zero failed requests across all eight runs (the benchmark client segfaulted on exit immediately after the 122B c8 run completed — a crash in its own cleanup path, not the server; results had already been written to disk and the server kept serving normally throughout, confirmed by its own request logs).

Reading the 35B/GPTQ tradeoff: at concurrency 1, GPTQ's 4-bit weights need less memory bandwidth per token than the 35B model's bf16 weights, so it's faster single-stream (14.34 vs 11.91 tok/s) and dramatically more consistent (p99 TTFT 2.2s vs a 36.5s outlier on the 35B run). Under concurrency 8, that flips — the 35B model's aggregate throughput pulls ahead (33.19 vs 26.13 tok/s) and its per-token latency degrades less (TPOT +183% vs GPTQ's +325% going from c1→c8), suggesting GPTQ's dequantization overhead scales worse with batch size on this ROCm backend than native bf16 does.
122B is the slowest tier at both concurrency levels — 7.87 tok/s at c1 (vs 11.91 and 14.34 for the other two) and only 16.05 tok/s at c8. The standout problem is absolute latency under load, not just the throughput gap: TPOT more than triples (119.88ms → 420.08ms) and mean TTFT balloons past 20 seconds — a request could sit for half a minute at p99 before its first token arrives with 8 concurrent requests in flight. --enforce-eager (required for this model's AWQ kernel path — disables CUDA graph capture and torch.compile) is the most likely explanation: eager-mode per-step overhead compounds badly once multiple requests are batched together. Whether a non-eager AWQ path becomes viable on this hardware is unverified — worth revisiting if this model's capability turns out to justify the speed cost.

Hardware & System Audit

  • GPU detection & memory allocation correct. gfx1151 initialized cleanly (all IP blocks loaded), GTT pool reports exactly 126976M ready — matches the intended ~124GB allocation. VRAM correctly shows only 1024M (deliberate minimal BIOS carve-out).
  • GPU compute confirmed active under load — 100% GPU utilization observed via rocm-smi during a live benchmark run, not a silent CPU fallback.
  • CPU governor was powersave on all 32 threads (running ~1.6-1.8GHz vs a 5GHz-capable CPU). Fixed declaratively to performance — confirmed base clock rose to ~2-2.9GHz even near-idle afterward.
  • rocm-smi's VRAM metric is misleading on this hardware — it only reports the 1GB static carve-out, not actual GTT/unified-memory usage (showed 208MB used while tens of GB were genuinely allocated). Added amdgpu_top and nvtop (AMD build) as correctly GTT-aware alternatives.
  • Router DNS resolver intermittently timing out — root cause of a cascade of downloads that appeared to fail from "network flakiness." Fixed with fallback resolvers (1.1.1.1, 8.8.8.8) behind the router, plus networking.networkmanager.dns = "none" (NetworkManager was silently ignoring the nameserver config otherwise — took two attempts to actually land).
  • Deprecated kernel param — amdgpu.gttsize is deprecated in favor of ttm.pages_limit (both currently set; redundant but harmless). Minor cleanup opportunity, not urgent.
  • Storage: 1.9TB NVMe, ext4, non-rotational, 10% used at time of writing. No I/O concerns.
  • Network correctly prefers wired (eno1) with WiFi as live fallback, as designed.
  • No real kernel errors — only benign split-lock/RAS-collector/USB-enumeration noise in the kernel log.

Resolved Since First Publish

  • Monitoring fully wired. Prometheus now scrapes all 5 targets successfully (added missing vLLM scrape configs, a real node-exporter container, and LiteLLM's prometheus callback — its /metrics route didn't exist at all without it). Grafana has a provisioned datasource and a real 10-panel dashboard, and its admin password was changed from the confirmed-still-active default.
  • Deployment pipeline redesigned and verified under real conditions, not just synthetically: nixos-rebuild switch was blocking 15-40 minutes on any push that touched a long-running download unit. Fixed with restartIfChanged = false plus converting downloads and docker-compose-app to timer-triggered units. Verified for real — not just a synthetic test — when the 122B download was killed mid-transfer to test resume behavior: a config push during its retry cycle completed in ~3.4s without disturbing it, and it resumed rather than restarting from scratch.
  • Real firewall bug found and fixed, in two stages: Docker's own FORWARD-chain rules were found to bypass NixOS's firewall entirely for published container ports (port 8000, raw vLLM/zero auth, was externally reachable despite never being allowlisted); the first fix (filterForward + trustedInterfaces) turned out to be incomplete — trustedInterfaces only exempts the input chain, not forward (matches a known upstream nixpkgs issue, #437920), which silently broke legitimate container-to-container traffic, including to already-allowlisted ports. Fixed with an explicit extraForwardRules rule plus a fixed docker bridge interface name (Docker's default auto-generated name changes every time the network is created, which would've silently broken this again on a fresh install).

Known Gaps & Next Steps

  • Turnstone has an empty model registry — judge/reranker role assignment (wiring the 4B model in as Turnstone's safety judge) has no env-var shortcut, needs TOML config or console UI work.
  • MTP (multi-token-prediction speculative decoding) deliberately not attempted — Qwen3-Next architecture supports it in vLLM (qwen3_next_mtp), but ROCm support is unconfirmed and tracked by an open upstream issue. Worth a dedicated feasibility check before investing engineering time, given the FP8 precedent on this same architecture family.
  • AITER fused MoE kernels untested — all three larger models here are MoE; this is a plausible low-risk throughput win worth an A/B test against this report's baseline.
  • Coding-capability comparison across all four models still needed — this report is speed/memory only. Given the 122B tier's poor speed, capability would need to be a decisive win to justify it.
  • Whether a non-enforce-eager AWQ path exists for the 122B model on this hardware is unverified — its bad concurrency scaling looks explainable by that flag, worth a follow-up if this model stays in consideration.
