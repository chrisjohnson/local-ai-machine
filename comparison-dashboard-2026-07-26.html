Biggest findings

  • Every model in the coding-capability table now shares the exact same 7-tier harness (22-task seven-tier-coding-v2) — a real improvement over the prior dashboard's mixed Tier-A/B-vs-six-tier comparison. Gemma-4-26B-A4B-it (vLLM (swap-in)) and Gemma-4-31B-it (vLLM) tie for the best score recorded: 22/22 (100%).
  • Two genuinely silent data-corruption bugs were found and fixed live during this sweep — both would have shipped wrong numbers if not caught. (1) Several vLLM builds (gemma-4-26b-a4b-it, gemma-4-31b-it, glm-4.7-flash-awq, qwen3.5-4b, qwen3.5-122b-a10b-awq4bit) were missing --enable-auto-tool-choice — the tool-call-parser flag alone isn't sufficient, so Tier B silently scored 0/5 on HTTP 400s that looked like real model failures. (2) The orchestrator's vLLM speed-benchmark trial code hardcoded port 8000 for every target; the production judge (port 8001) had every request fail instantly, and the only validation was "does the result file exist" — the all-zero data sailed through as if real. Both fixed, all affected builds re-recorded clean. See Data Quality for the full bug list.
  • The small-active-param-MoE pattern from the prior dashboard holds up under much more data. GLM-4.7-Flash is the fastest llama.cpp-direct model measured (71.24 tok/s tg128), and Qwen2.5-VL-7B-Instruct leads vLLM c8 throughput (94.54 tok/s) — both small-active-param MoE models. Dense models (Qwen3.6-27B at 12.72 tok/s llama.cpp, Gemma-4-31B-it at 11.24 tok/s vLLM c8) trail badly, consistent with every prior measurement on this hardware.
  • Two brand-new 120B-class models were benchmarked for the first time this pass — NVIDIA-Nemotron-3-Super-120B-A12B (hybrid Mamba2/MoE/attention, 17.62 tok/s tg128, 20/22 coding) and MiniMax-M2.7 (228.69B total, the largest model tested on this box, 30.88 tok/s tg128 despite its size — Q3_K_S quantization and MoE routing both doing real work here). Both are UNTESTED-BUT-DOWNLOADED status — real first-look data, not yet a settled recommendation.
  • GPT-OSS-120B's c1 throughput improved substantially on re-test (8.74 tok/s here vs 8.46 tok/s previously — within noise) but its coding score dropped from the prior dashboard's headline 11/12 to 20/22 (90.9%) under the harder 7-tier harness, missing judge_incorrect (Tier J) again and a new debugging (Tier D) miss not seen before — a harder, more apples-to-apples test surfacing a real gap the smaller harness didn't.
  • The recurring judge_incorrect (Tier J) failure from the prior dashboard is now confirmed across far more models. 13 of 19 builds tested this pass missed at least one Tier J task — still the single most consistent cross-model weakness measured on this hardware. No model tested so far should be trusted as an unsupervised LLM-judge.
  • Qwen2.5-VL-7B-Instruct now holds the best concurrency headroom recorded (51.61× @32768, beating GPT-OSS-20B's prior-best 30.02×) — expected given its small 7B dense size and short served context, but its coding score (68.2%, driven by an 0/5 Tier B miss) confirms it's a vision/OCR specialist as documented, not a coding candidate.

Data quality — an honest accounting

Real bugs found and fixed during this pass (all verified via clean re-run)

  • Missing --enable-auto-tool-choice on 5 builds silently zeroed Tier B. gemma-4-26b-a4b-it, gemma-4-31b-it, glm-4.7-flash-awq, qwen3.5-4b (judge), and qwen3.5-122b-a10b-awq4bit all had --tool-call-parser set without the enable flag the standing production services also carry — every tool-calling request got HTTP 400, scored as a model failure rather than a config gap. All five fixed, contaminated runs stripped, re-recorded clean.
  • Hardcoded port 8000 in the vLLM speed-trial code corrupted the production judge's data. Every speed trial hit localhost:8000 regardless of which container was actually targeted — harmless for the primary/swap-in candidates (really on 8000), but the judge serves on 8001. Every request failed instantly; the only validation was "does the result file exist," so all-zero data was committed as if real. Fixed by threading the real port through properly, plus a hard completed=0 guard added so this class of bug can't recur silently.
  • 4 of the original 6 queued downloads sat failed for ~23 hours from an early preflight pause whose matching resume never ran. Found during routine monitoring, resumed manually.
  • hfExclude glob patterns silently stopped excluding metal/* for the two GPT-OSS vLLM downloads (likely an hf-cli version drift since this was last verified working) — both crash-looped forever on a 65GB file that was supposed to be skipped. Switched to an explicit file allowlist (verified against the live HF API) instead of chasing the glob mismatch further.
  • Every one of the above was caught by direct verification, not assumed from a clean exit code — cross-checking real trial data (completed/failed counts, non-zero throughput) against what the harness reported, and a full post-sweep audit of every build's tier scores for suspicious 0/N patterns before trusting this dashboard's numbers.

Engines / models still untested, excluded, or broken

  • Ollama excluded from this entire pass, deliberately. The currently-registered Ollama models (qwen3.6-35b-a3b-gguf etc.) have a broken bare-passthrough chat template (TEMPLATE {'{'} .Prompt {'}'}", no tool-calling schema, <think> blocks leak into content unparsed) — confirmed via curl .../api/show and via harness runs scoring far worse than llama-server on identical tasks for template reasons, not real model-quality differences. Fixing needs a real Go-template translation of each model's chat template, deliberately out of scope this pass to avoid producing bad data under time pressure.
  • llamacpp-gpt-oss-120b (the single-file GGUF repack) downloaded successfully but was never benchmarked — its download hit the identical metal/*-exclusion failure as the vLLM repos, but as a single-file repo there's nothing to allowlist around. The file needs hf_xet, which this project deliberately disables globally because it hangs on this network path for other models. Deferred, not silently dropped — needs a real decision (try installing hf_xet and testing it just for this repo, or accept the gap).
  • north-mini-code-1.0-w4a16 has an unresolved --max-model-len <tbd> placeholder in its build config — never finished being set up before this pass, so the orchestrator correctly skips it every run rather than guess a value.
  • MTP (multi-token-prediction) speculative decoding remains unbenchmarked for both Qwen3.6 GGUF variants — carried over from the prior dashboard, unchanged this pass.

Known methodology notes carried forward

  • vLLM numbers are now 3-trial-averaged (vllm-speed-c1c8-v2), not single-run — a real rigor improvement over the prior dashboard's single-sample vLLM figures, adopted specifically "for any build being seriously considered as a new production default or role-replacement candidate."
  • llama.cpp and vLLM numbers for the same model are still not directly comparable — different serving stacks, different batching/scheduling behavior, different quantization in most cases. Read within-engine rankings as reliable, cross-engine gaps as directional.
  • Every run-fingerprint (kernel, GPU driver, image digest, engine version, repo commit, concurrent-load state, host-metrics time window) is captured fresh per run and stored alongside the result in catalog/builds/*.yaml — full provenance for every number in this dashboard, not just a headline figure.
