# M-086.1 — pi-web-factory — per-Workflow /skill:<name> commands, SSSF-style shorthand

## Context
**Renumbered from M-086 due to an ID collision** — `M-086` was already taken by an
unrelated, unclaimed card ("Research dflash laguna", laguna performance tuning) at
the time this was filed. Per `AGENTS.md` §6a, renumbered with a `.1` suffix rather
than overwriting; the original M-086 is untouched.

Chris, 2026-08-05: "Like the original SSSF I'm thinking something like /workflow-name
<initial prompt>" — wanted a more direct, SSSF-like trigger ergonomic than M-072's
single natural-language-routing skill. Research found pi's real, native mechanism for
exactly this: Skills auto-register as `/skill:<name>` commands
(`@earendil-works/pi-coding-agent`'s own `docs/skills.md`), with trailing args
appended to the skill's loaded content as the next user message — confirmed via
direct read of the installed package's docs, not assumed.

## Plan
1. [x] Split the single M-072 routing-table skill into one dedicated skill PER
   registered Workflow (`plan-build-review`, `bounded-build-review`,
   `plan-build-test`), each named to match its Workflow exactly — so
   `/skill:plan-build-review <task>` triggers that Workflow directly, no
   natural-language inference needed.
2. [x] Kept the original `pi-web-factory` skill too (Chris: "I'm totally ok with a
   natural language skill too. I just want some way to trigger it") — now
   cross-references the three dedicated skills for users who already know the
   shape they want, and remains the fallback for open-ended requests.
3. [x] `enableSkillCommands: true` — required for `/skill:` commands to actually
   register. Live in `settings.json` on the box, which is deliberately NOT
   re-synced from git like everything else (user-editable by design) — set both
   directly on the live file AND in `settings.seed.json` per Chris's explicit
   instruction on how this file is properly managed ("adjusting the seed file,
   deleting it from ~/.pi-web, re-building the image... You can feel free to
   adjust the live file in-place but make sure to update the seed file to match").
4. [x] Dockerfile/entrypoint: sync the whole `skills/` directory generically (by
   subdirectory name, never a wholesale `rm -rf $CONFIG_ROOT/skills`) so a new
   skill is a new subdirectory, not a Dockerfile edit, and any skill a human adds
   by hand to the live config dir is never clobbered by the sync.
5. [x] Deployed (`docker compose build/up jmfederico-pi-web`), verified live: a
   fresh ordinary session's system prompt auto-loaded the skill content
   (`<skill name="plan-build-review" ...>` visible in the real transcript) when
   sent the literal `/skill:plan-build-review <task>` message — the mechanism
   itself works exactly as documented, no ambiguity, no inference needed.
