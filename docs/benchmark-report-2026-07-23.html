Reading the 35B/GPTQ tradeoff (2026-07-22, still holds): at concurrency 1, GPTQ's 4-bit weights need less memory bandwidth per token than the 35B model's bf16 weights, so it's faster single-stream (14.34 vs 11.91 tok/s) and dramatically more consistent (p99 TTFT 2.2s vs a 36.5s outlier on the 35B run). Under concurrency 8, that flips — the 35B model's aggregate throughput pulls ahead (33.19 vs 26.13 tok/s).
Dense models consistently underperform MoE models on this bandwidth-bound hardware — the single clearest finding from the four new models. Qwen3.6-27B (dense, all 27B params active per token) is slower than the 35B-A3B primary (MoE, ~3B active) at both concurrency levels despite having fewer total parameters — 4.07 vs 11.91 tok/s @c1, 17.91 vs 33.19 @c8. Gemma-4-31B-it (dense) is the slowest model tested all session at 3.23/11.73 tok/s, with p99 TTFT ballooning to nearly a minute (59.2s) at concurrency 8. Meanwhile Gemma-4-26B-A4B-it (MoE, ~4B active — similar active-parameter budget to the 35B-A3B primary but a smaller total footprint) is the fastest model tested all session at both concurrency levels: 20.85/50.38 tok/s, beating even the current production primary.

Coding-Capability Results

Speed and memory footprint say nothing about whether a model can actually write correct code or use tools reliably — this was the single biggest gap flagged in the 2026-07-22 report. A new harness (scripts/coding_benchmark.py) fills it with two objective, non-LLM-judged grading tiers: Tier A — 3 correctness tasks (palindrome check, merge-sorted-lists, arithmetic expression parser), graded by executing the model's extracted code against real test assertions in a sandbox. Tier B — 2 tool-calling tasks (single call; a multi-step write-then-test sequence), graded structurally against the expected tool schema/arguments. Run against all 7 non-vision models (Qwen2.5-VL-7B is a vision/OCR specialist, excluded as not a coding candidate).

Tier B (tool-calling) was perfect across every single model tested — 2/2, no exceptions. All Tier A shortfalls came from the same one task each time (though not always the same task across models): a reasoning model occasionally exhausts its token budget mid-thought on a task before ever committing to a final answer, rather than a genuine inability to solve it. This was root-caused during harness development (see below), not treated as a capability gap.
The current production primary is not the strongest coding performer. Four other models — including both size tiers already in the comparison rotation (80B GPTQ, 122B AWQ) and both Gemma candidates — scored a perfect 5/5, while the primary landed at 4/5. Gemma-4-26B-A4B-it in particular combines the fastest speed of any model tested with a perfect coding score, making it the single strongest result in this report. This is a real signal worth weighing before any primary-swap decision, not a close call to shrug off.
Caveat on the primary's 4/5: its result was captured before the final harness bug fix (a fallback for extracting code from a model's reasoning trace when its final answer field comes back empty) — the exact failure mode its palindrome miss hit. It wasn't re-run under the final harness version like the other six models were, so 4/5 is likely a conservative floor rather than a fully apples-to-apples number. A one-off re-run would clean this up.
Harness development found 6 real bugs, each surfaced only by running against a live model, not visible from the design on paper: (1) Tier A's initial 1024-token budget was too small for reasoning models, entirely consumed by the thinking trace; (2) the request timeout was initially too short for slower models' full-length responses; (3) code extraction initially grabbed the first markdown fence instead of the last, sometimes pulling a draft instead of the final answer; (4) Tier B's tool-calling budget had the same too-small-budget problem as Tier A initially did; (5) a model can still exhaust budget mid-thought even at a generous cap, needing a fallback to extract code from the reasoning trace itself; (6) the harness didn't catch TimeoutError specifically, so one slow-model timeout crashed the whole run instead of failing just that task. All fixed and verified against real runs before trusting the final numbers above.

Hardware & System Audit

  • GPU detection & memory allocation correct. gfx1151 initialized cleanly (all IP blocks loaded), GTT pool reports exactly 126976M ready — matches the intended ~124GB allocation. VRAM correctly shows only 1024M (deliberate minimal BIOS carve-out).
  • GPU compute confirmed active under load — 100% GPU utilization observed via rocm-smi during a live benchmark run, not a silent CPU fallback.
  • CPU governor was powersave on all 32 threads (running ~1.6-1.8GHz vs a 5GHz-capable CPU). Fixed declaratively to performance — confirmed base clock rose to ~2-2.9GHz even near-idle afterward.
  • rocm-smi's VRAM metric is misleading on this hardware — it only reports the 1GB static carve-out, not actual GTT/unified-memory usage. Added amdgpu_top and nvtop (AMD build) as correctly GTT-aware alternatives.
  • Real, currently-unresolved security finding (2026-07-23): raw vLLM on port 8000 (zero auth) is reachable from off-box over the LAN despite being deliberately excluded from the firewall's allowlist — confirmed directly. The earlier filterForward/extraForwardRules fix (see below) likely never actually closed the original Docker-forward-chain bypass for published container ports specifically; NixOS's firewall has an unconditional ct status dnat accept rule to make Docker's NAT'd traffic work at all, which plausibly accepts any DNAT'd connection regardless of destination port. Root cause not yet confirmed (needs interactive sudo access this session couldn't provide) — worked around with an SSH tunnel for benchmarking in the meantime. Real fix still open.
  • Router DNS resolver intermittently timing out — root cause of a cascade of downloads that appeared to fail from "network flakiness." Fixed with fallback resolvers plus networking.networkmanager.dns = "none".
  • Storage: 1.9TB NVMe, ext4, non-rotational. No I/O concerns.
  • No real kernel errors — only benign split-lock/RAS-collector/USB-enumeration noise in the kernel log.

Resolved Since First Publish

  • Monitoring fully wired. Prometheus scrapes all 5 targets; Grafana has a provisioned datasource, a real 10-panel dashboard, and a non-default admin password.
  • Deployment pipeline redesigned and verified under real conditions. nixos-rebuild switch no longer blocks 15-40 minutes on long-running download units — fixed with restartIfChanged = false plus timer-triggered units. Verified for real when a download was killed mid-transfer during a config push and resumed correctly.
  • Firewall bug found and "fixed" in two stages — but see the new finding above. Docker's own FORWARD-chain rules were found to bypass the firewall entirely for published container ports; the first fix (filterForward + trustedInterfaces) was incomplete (didn't cover the forward chain), fixed again with extraForwardRules. This report's own testing (2026-07-23) found port 8000 externally reachable again — the fix likely never fully closed the gap for DNAT'd/published-port traffic specifically. Not a regression from a code change; more likely this was never fully fixed. See Hardware & System Audit above.
  • Download reliability hardened. Downloads serialized with a shared flock after parallel downloads were found saturating the connection; a stall watchdog added after a genuine hung-TCP-connection failure mode (data arriving, never consumed, no error) was found separate from earlier DNS-timeout issues.

Known Gaps & Next Steps

  • Firewall gap is real and unresolved — see Hardware & System Audit above. Needs interactive sudo access to read the live nftables ruleset and find the actual fix.
  • Primary model's coding-capability score (4/5) predates the harness's final bug fix — worth a one-off re-run for a fully apples-to-apples comparison against the other six models' 4/5-or-5/5 scores.
  • Optimization phase not yet started, in priority order: (a) AITER fused MoE kernels for the MoE models — needs verification first, since the 122B config already explicitly overrides away from AITER, hinting at a known interaction issue, not a blind toggle; (b) whether a non-enforce-eager AWQ path is viable for the 122B tier, since enforce-eager looks like the main driver of its (still-perfectly-capable, just slow) concurrency scaling; (c) --max-num-batched-tokens/chunked-prefill tuning; (d) MTP speculative decoding last, treated as a real experiment given unconfirmed ROCm support and the FP8 precedent on the same architecture family.
  • Turnstone still has an empty model registry — judge/reranker role assignment needs TOML config or console UI work, unrelated to this benchmarking effort.
  • A future post-optimization run should re-benchmark both speed and coding-capability into a new, directly comparable HTML report against this one.
