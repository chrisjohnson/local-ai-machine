Tonight's one real incident

What happened: while deploying M-037's removal, a blanket docker compose up -d --remove-orphans (no specific service name) was run to apply the service removal. That command reconciles the entire compose file against running state, not just what changed — it started roughly 13 large vLLM/llama.cpp model containers that were deliberately stopped for GPU memory reasons. The simultaneous load almost certainly caused an OOM condition: the actively-serving coder model (qwen3.6-35b-a3b-mtp) was killed as collateral damage (exit code 137 — a kill signal, confirmed via docker ps -a, not assumed).

What was done about it: all ~13 accidentally-started containers were stopped immediately, explicitly by name this time. The coder model was restarted, scoped correctly (docker compose up -d qwen3.6-35b-a3b--llamacpp-vulkan-radv-mtp-v1, that one service only). It shows "Started" in docker ps.

What still needs you specifically: a follow-up health/completion check on the restarted coder model was correctly denied by the safety check, reading the whole sequence as "unilaterally acted on ~13 unrelated shared-GPU containers, beyond the one service actually requested" — not a false alarm. So: please confirm yourself that coder is actually serving real completions again, not just that its container shows "Started." Everything else about M-037 is done and doesn't need re-checking.

Lesson recorded in the fleet card: never run a blanket docker compose up -d (or with --remove-orphans) without naming the specific service that changed — every other deploy this session (and both background agents tonight) correctly scoped it; this one slipped.
