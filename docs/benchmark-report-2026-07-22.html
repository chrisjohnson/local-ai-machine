All runs: vllm bench serve, random dataset, --ignore-eos (fixed output length for clean throughput comparison), 20-40 prompts per run. Zero failed requests across all six runs.

Reading the tradeoff: at concurrency 1, GPTQ's 4-bit weights need less memory bandwidth per token than the 35B model's bf16 weights, so it's faster single-stream (14.34 vs 11.91 tok/s) and dramatically more consistent (p99 TTFT 2.2s vs a 36.5s outlier on the 35B run). Under concurrency 8, that flips — the 35B model's aggregate throughput pulls ahead (33.19 vs 26.13 tok/s) and its per-token latency degrades less (TPOT +183% vs GPTQ's +325% going from c1→c8), suggesting GPTQ's dequantization overhead scales worse with batch size on this ROCm backend than native bf16 does.

Hardware & System Audit

  • GPU detection & memory allocation correct. gfx1151 initialized cleanly (all IP blocks loaded), GTT pool reports exactly 126976M ready — matches the intended ~124GB allocation. VRAM correctly shows only 1024M (deliberate minimal BIOS carve-out).
  • GPU compute confirmed active under load — 100% GPU utilization observed via rocm-smi during a live benchmark run, not a silent CPU fallback.
  • CPU governor was powersave on all 32 threads (running ~1.6-1.8GHz vs a 5GHz-capable CPU). Fixed declaratively to performance — confirmed base clock rose to ~2-2.9GHz even near-idle afterward.
  • rocm-smi's VRAM metric is misleading on this hardware — it only reports the 1GB static carve-out, not actual GTT/unified-memory usage (showed 208MB used while tens of GB were genuinely allocated). Added amdgpu_top and nvtop (AMD build) as correctly GTT-aware alternatives.
  • Router DNS resolver intermittently timing out — root cause of a cascade of downloads that appeared to fail from "network flakiness." Fixed with fallback resolvers (1.1.1.1, 8.8.8.8) behind the router, plus networking.networkmanager.dns = "none" (NetworkManager was silently ignoring the nameserver config otherwise — took two attempts to actually land).
  • Deprecated kernel param — amdgpu.gttsize is deprecated in favor of ttm.pages_limit (both currently set; redundant but harmless). Minor cleanup opportunity, not urgent.
  • Storage: 1.9TB NVMe, ext4, non-rotational, 10% used at time of writing. No I/O concerns.
  • Network correctly prefers wired (eno1) with WiFi as live fallback, as designed.
  • No real kernel errors — only benign split-lock/RAS-collector/USB-enumeration noise in the kernel log.

Any future third permanent tier needs either a smaller judge allocation or a full re-budget of the 0.70/0.20 split.

Known Gaps & Next Steps

  • Grafana is running but non-functional — no Prometheus datasource provisioned, dashboard file is an empty placeholder ("panels": []), and Prometheus itself has no scrape target for either vLLM server despite both exposing rich /metrics endpoints. litellm and node scrape targets are both currently down (the latter points at a node-exporter container that doesn't exist).
  • Grafana still on default admin:admin credentials, confirmed still active — needs a real password before this is exposed any further.
  • Turnstone has an empty model registry — judge/reranker role assignment (wiring the 4B model in as Turnstone's safety judge) has no env-var shortcut, needs TOML config or console UI work.
  • MTP (multi-token-prediction speculative decoding) deliberately not attempted — Qwen3-Next architecture supports it in vLLM (qwen3_next_mtp), but ROCm support is unconfirmed and tracked by an open upstream issue. Worth a dedicated feasibility check before investing engineering time, given the FP8 precedent on this same architecture family.
  • AITER fused MoE kernels untested — both models here are MoE-heavy; this is a plausible low-risk throughput win worth an A/B test against this report's baseline.
  • Coding-capability comparison between 35B and 80B GPTQ still needed — this report is speed/memory only.
