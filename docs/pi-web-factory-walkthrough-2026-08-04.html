pi-web-factory

A deterministic control plane for AI coding agents, built on top of your existing jmfederico-pi-web stack. As of today it's fully baked into the live container, triggerable from inside any ordinary pi-web session via a slash command, and has a real dashboard of its own. This page leads with how you'll actually use it day to day — the CLI section further down is for scripted/ advanced use, not the normal path.

What is this?

pi-web-factory brings the SSSF pattern — deterministic code owns sequencing, retries, and acceptance; an AI agent works inside one bounded, typed Step at a time — to your running pi-web deployment. It drives real pi-web sessions over the same HTTP/WebSocket API your browser uses.

The practical upshot: every session pi-web-factory starts is a completely ordinary pi-web session, in its own git worktree, registered as a real pi-web Project. It shows up in the browser UI exactly like one you started by hand, with a real, working deep-link. You can watch an agent work in real time, and if something needs a human, you can even answer it there.

Why it exists

  • Typed output, every time. An agent Step's only real output is one JSON object matching a schema declared up front. If it doesn't parse, the harness re-prompts the same session with a correction naming exactly what was wrong — never a cold restart.
  • Enforced write boundaries. Every agent Role has a writes: allowlist. Anything it touches outside that allowlist gets rolled back automatically, and the Step is reported as failed, not silently patched up.
  • A full trace. Every Step, every tool call, every gate result, every token count lands in a local SQLite db (factory.db) as it happens, browsable in the visualizer or queryable directly.
  • Workflows are data, not code. A new sequence of Steps — including a bounded correction loop — is a YAML file, not a new TypeScript module.
  • Isolation by default. Every Workflow Run gets its own git worktree and branch, so concurrent runs (or a run alongside your own manual work) never collide.

Terminology

Workflow Run
One top-level, open-ended prompt execution — "do X." Has its own adwId, its own git worktree, its own pi-web session, and its own row of observability data.
Workflow
A named, YAML-configured, reusable template describing an ordered sequence of Steps a Workflow Run executes — e.g. plan-build-review.
Step
One unit inside a Workflow: either kind: agent (a pi-web prompt/response turn) or kind: code (a plain subprocess, no model call). A kind: loop Step repeats its inner Steps up to a bound.
Role
A unified agent/code identity — plan, build, review, run-tests, etc. Carries model, thinking level, write allowlist, and (for agent Roles) a real system prompt.

Triggering work — /skill: commands

This is the normal way to use pi-web-factory: from inside any ordinary pi-web session, sitting in a project you're already working in, just say what you want.

Two ways to trigger it, both real, native pi mechanisms:
  • Explicit, SSSF-style shorthand — /skill:plan-build-review <task>, /skill:bounded-build-review <task>, or /skill:plan-build-test <task> — pick the Workflow, pi loads that skill and runs it directly. No ambiguity.
  • Natural language — just describe what you want ("run the pipeline to add a health endpoint and review it"). The general pi-web-factory skill picks the right Workflow for you.

Example — typed directly into an ordinary pi-web session's message box:

/skill:plan-build-review Add a /health endpoint that returns 200 OK

What happens next, automatically, inside that same conversation:

  1. pi loads the skill's instructions (confirmed live — the very first thing that happens is the skill's own content appearing in the transcript).
  2. The model figures out your project path from its own session (usually just pwd — it's already sitting in the right place) and runs bun $HOME/pi-web-factory/cli.ts --project <path> --workflow plan-build-review "<task>" via its own bash tool.
  3. That mints a separate, real Workflow Run — its own git worktree, its own pi-web session, its own full agent-vs-agent plan/build/review sequence. This takes real time; the triggering session waits for it.
  4. When it's done, the triggering session relays a clean summary back to you, including a real deep-link to the resulting session — not raw CLI output.
This is pi's real, native Agent Skills mechanism — skills auto-register as /skill:<name> commands, and the description text is what the model matches against for the natural-language path. Nothing custom was built to make this work; the two-mode design was already there, this project just uses it.

The three shipped Workflows

TriggerShapePick it when…
/skill:plan-build-reviewplan → build → review (no loop)a clear task where one review pass is enough — the default choice.
/skill:bounded-build-reviewbuild → loop{review, build} until approved, max 3 roundsyou want correction rounds baked in, or the task is finicky/security-sensitive.
/skill:plan-build-testplan → build → test (a real command, not another agent)you want a mechanical, code-based acceptance check — needs the project to have a .pi-web-factory.yaml declaring its test command.

All three are just entries in chains/registry.ts; adding a fourth shape is a YAML file, not new TypeScript.

The visualizer

A real-time dashboard over every Workflow Run's trace data, restyled to match pi-web's own configured theme exactly (same colors, same fonts, same light/dark "Auto" behavior — pulled straight from pi-web's own shipped theme tokens, not approximated), live at:

Open the visualizer → http://192.168.1.226:8090

Deployed as its own compose service (reusing the same image pi-web-factory is baked into, M-068) — comes up and down with the rest of the stack, no separate process to remember to start.

A live-updating grid, SSSF-style

The main page is a responsive grid of cards — every Workflow Run visible at a glance, each with its own condensed live timeline, no click-through needed just to see what's happening. Sort order is deliberate: still-running runs first (oldest-started at the very top), then completed runs newest-first below.

Light theme (pi-web's own sand/purple palette). Real, descriptive titles now (derived from the task prompt at Workflow Run start — "Add rate limiting middleware that returns H…" — not the bare adwId), a purple pulsing-glow border on the running card, green-tinted successes and red-tinted failures, both dimmed slightly to read as "done, not active."
The same page, dark theme — follows your system's light/dark preference automatically via prefers-color-scheme, exactly like pi-web's own "Auto" mode.

Detail view — click any card for the full timeline

Clicking a card still drops you into the full per-Step Gantt timeline (kept from the original design) — each Step's bar is drawn proportional to its real duration, gaps between Steps compressed to a small fixed width rather than drawn to scale, so a run that sat blocked-on-human for an hour won't produce an hour-long blank stretch. Each Role now gets its own persistent color (purple/plan, teal/build, gold/review, blue/scout, pink/document, green/run-tests) — the same palette shows up in the grid's condensed timelines too.

Filtered by project

Selecting a project groups every run triggered against it — regardless of which git worktree each individual run actually used under the hood (a real bug found and fixed live, see the findings below).

Watching it live in pi-web's own UI

Every Workflow Run's Steps are ordinary pi-web sessions underneath — real iterative work, not a single canned response. This one diagnosed a failing test, fixed it, reran until all 26 passed, then committed — you can always drop into pi-web's own browser UI (the deep-link every result carries) and watch it happen exactly as if you'd started it by hand.

What we learned running it for real

A live testing pass today (multiple real Workflow Runs, real failures, real infra hiccups) surfaced several genuine findings — some already fixed, some flagged for a later decision.

Fixed today

Error messages now say what actually happened

The single biggest complaint: a failed run used to just say a generic, unhelpful sentence — no way to tell what actually went wrong. Now the agent's real raw response (or an explicit "returned no response text at all" for a genuinely empty one) and the actual violating filename(s) are surfaced directly.

Before
UNPARSEABLE — the agent's response never matched the required envelope schema after retries
After
UNPARSEABLE — the agent returned no response text at all (empty) after retries
Before
PERMISSIONS-VIOLATION — the agent wrote outside its allowed paths; changes were rolled back
After
PERMISSIONS-VIOLATION — the agent wrote outside its allowed paths (stack.py); changes were rolled back
Real finding

Ornith (the newly-swapped medium-moe backend) is a genuine reasoning model

A direct completion test against it returned an empty content field with a non-empty reasoning_content field and finish_reason: "length" — it exhausted its token budget entirely inside invisible "thinking" before emitting any real output. This is very likely the actual cause of most of today's empty-response failures, not model "misbehavior" — qwen (the previous backend) had special handling elsewhere in this stack for exactly this class of problem, which pi-web-factory's own Role config doesn't yet have. Switched back to qwen for stability; a smaller Ornith quant (Q4_K_M, ~20.6GB, MTP tensors verified) is downloading in the background for more memory headroom to experiment further later.

Flagged, not fixed

A rejected review can still report top-level SUCCESS

Found live: a build Step claimed it wrote a file that, in fact, was never written. review correctly caught the discrepancy in its own summary — but plan-build-review has no loop and does no post-processing on approved, so the overall Workflow Run still came back SUCCESS. Filed for a real design decision (does a no-loop review-ending Workflow need its own distinct "rejected" outcome, or is the fix just surfacing approved/findings more visibly?) rather than a unilateral patch.

Flagged, not fixed

Permissions enforcement can flag harmless verification artifacts

A read-only review Step legitimately ran the code it was reviewing to check it actually works — which left behind a Python __pycache__/*.pyc file, correctly detected as an unauthorized write and rolled back. The rollback is working exactly as designed; the open question is whether well-known incidental build artifacts (bytecode caches, etc.) should get a default exemption.

Operational

Two large models co-resident leaves almost no memory headroom

With big-moe (118B) and medium-moe (35B) both loaded, the box sits at roughly 122GB/124GB used — running two concurrent agentic test Workflows was enough to trip the OOM killer on the smaller model, twice, in one afternoon. Also found (separately) a real port-binding bug where a container's declared port mapping silently wasn't active despite a matching compose config — a plain restart didn't fix it, a force-recreate did.

Architecture

Config/data modules, the generic interpreter, a thin chain layer, a CLI, skills, and the visualizer — all baked into the same jmfederico-pi-web image and always re-synced on container start, so the running copy never drifts from what's committed to git.

roles.ts
The unified Role registry — agent + code, real system prompt files resolved per agent Role.
workflowDef.ts
The Workflow YAML schema: agent/code/loop Steps, load-time validation.
workflow.ts
The generic interpreter. Walks any Workflow's Steps, runs loops, records every result.
tracer.ts
Writes every Workflow Run / Step / event / gate result / token count to factory.db.
piwebClient.ts
The only module that talks to pi-web's session API.
piwebProject.ts
Registers the target project as a pi-web Project, resolves its workspace id.
worktree.ts
Creates one git worktree + branch per Workflow Run.
envelopes.ts / gates.ts
Required JSON output schemas; after-the-fact verification of claims.
permissions.ts
Snapshots the repo before/after a turn; rolls back anything outside the allowlist.
run.ts
The shared agent-Step runner — parse-retry loop, permissions enforcement, real failure detail capture.
skills/*/SKILL.md
The four pi Agent Skills — one per Workflow plus the general router — baked in and always-synced.
visualizer/
Read-only Bun.serve dashboard over factory.db, its own compose service.
cli.ts
The command a Skill (or a human) actually invokes. Argument parsing and I/O only.
Per-project config lives in the project, not here. <project>/.pi-web-factory.yaml declares that project's own test/typecheck/lint commands. pi-web-factory's own factory.config.yaml only holds the shared Role registry.

How a Workflow Run flows

Walking through bounded-build-review — build → loop{review, build} until approved (max 3 rounds) — since it exercises every mechanism the simpler Workflows share, plus the loop.

1

Triggered — via /skill: command or cli.ts directly

--project, --workflow, and your prompt get validated. An unknown project config or Workflow name fails immediately with a specific message, not a stack trace.

2

A fresh git worktree is created for this Workflow Run

<project>/.pi-web-factory-worktrees/<adwId>, on a new branch, invisible to the target project's own tracked files. The project gets registered as a pi-web Project if it isn't already.

3

A pi-web session starts, pointed at the worktree

One real session, same kind the browser UI creates. It gets threaded through every Step in this Workflow Run.

4

Step 1 — build (agent, medium-moe)

Gets a true system prompt (a real pi extension, not prepended text). The repo is snapshotted before and after; anything written outside build's allowlist is rolled back and the Step fails as permissions-violation — with the actual filename now, not just a generic message.

↻

Loop — review → (rejected?) → build → …

review (agent, big-moe, read-only) returns {approved: boolean, findings: [...], blocking: [...]}. If rejected, the interpreter builds a correction message from the concrete blocking findings and re-runs build in the same session. Capped at 3 rounds; a real, distinct loop-exhausted outcome if it never converges.

✓

Result — a 7-way discriminated outcome, relayed back to you

success, blocked-on-human, unparseable, permissions-violation, failed, gate-failed, or loop-exhausted — every branch carries the real deep-link, and every failure branch now carries real diagnostic detail.

Advanced: driving cli.ts directly

The /skill: commands are the normal path — this is for scripting, automation, or debugging. From inside the pi-web container (or via the same command a Skill runs under the hood):

bun $HOME/pi-web-factory/cli.ts --project /path/to/project \
  --workflow bounded-build-review \
  "Add a /health endpoint that returns 200 OK"

The prompt can also be a path to a file. Resume a session blocked on a question:

bun $HOME/pi-web-factory/cli.ts --project /path/to/project \
  --workflow plan-build-review \
  --session-id 019fcb42-c0f9-73fb-881f-b80c1b232778 \
  "continue"

Exit codes

CodeMeaning
0Success.
1Failed (a Step errored outright).
2Blocked on a human — the agent asked a question mid-turn.
3Unparseable — an agent Step never produced valid JSON after retries.
4Permissions violation — a Step wrote outside its allowlist (rolled back).
5Gate failed — a code Step's checks didn't pass.
6Loop exhausted — a loop Step's until condition was never satisfied within max_rounds.
64Usage/config error — bad flags, unknown project, or unknown Workflow.

Worktrees, Projects & real deep-links

Every Workflow Run gets its own git worktree under <project>/.pi-web-factory-worktrees/<adwId>, on its own branch — concurrent runs never collide, and never touch your own manual work in the project's main checkout. The target project is auto-registered as a real pi-web Project, and every result carries a real, working deep-link:

http://192.168.1.226:8080/?project=<id>&workspace=<id>&session=<id>

Note: the visualizer's project filter groups by the real, shared project root, not each run's own unique worktree path — see the visualizer section above.
