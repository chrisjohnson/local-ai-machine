pi-web-factory

A deterministic control plane for AI coding agents, built on top of your existing jmfederico-pi-web stack. This page reflects the architecture as of the evening autonomous session on 2026-08-04 — a significant redesign from the first cut of this doc, driven by real feedback: per-project config that lives with the project, real git-worktree isolation per run, true per-role system prompts, and a fully data-driven Workflow interpreter instead of one hand-written TypeScript file per shape.

What is this?

pi-web-factory brings the SSSF pattern — deterministic code owns sequencing, retries, and acceptance; an AI agent works inside one bounded, typed Step at a time — to your running pi-web deployment. Instead of spawning a bare pi CLI subprocess (which doesn't exist on PATH anywhere in the jmfederico-pi-web container), it drives real pi-web sessions over the same HTTP/WebSocket API your browser uses.

The practical upshot: every session pi-web-factory starts is a completely ordinary pi-web session, in its own git worktree, registered as a real pi-web Project. It shows up in the browser UI exactly like one you started by hand, with a real, working deep-link. You can watch an agent work in real time, and if something needs a human, you can even answer it there — something the upstream SSSF tool can't do at all, since it has no equivalent UI.

Why it exists

  • Typed output, every time. An agent Step's only real output is one JSON object matching a schema declared up front. If it doesn't parse, the harness re-prompts the same session with a correction naming exactly what was wrong — never a cold restart.
  • Enforced write boundaries. Every agent Role has a writes: allowlist. Anything it touches outside that allowlist gets rolled back automatically, and the Step is reported as failed, not silently patched up.
  • A full trace. Every Step, every tool call, every gate result, every token count lands in a local SQLite db (factory.db) as it happens, queryable independently of pi-web's own session history.
  • Workflows are data, not code. A new sequence of Steps — including a bounded correction loop — is a YAML file, not a new TypeScript module. One generic interpreter runs any of them.
  • Isolation by default. Every Workflow Run gets its own git worktree and branch, so concurrent runs (or a run alongside your own manual work) never collide.

Terminology

Formalized this session, used consistently everywhere below — in the code, the board cards, and the design doc:

Workflow Run
One top-level, open-ended prompt execution — "do X." Has its own adwId, its own git worktree, its own pi-web session (usually), and its own row of observability data.
Workflow
A named, YAML-configured, reusable template describing an ordered sequence of Steps a Workflow Run executes — e.g. plan-build-review. Not hardcoded per-shape TypeScript.
Step
One unit inside a Workflow: either kind: agent (a pi-web prompt/response turn) or kind: code (a plain subprocess, no model call). Every Step names a Role. A kind: loop Step repeats its inner Steps up to a bound.
Role
A unified agent/code identity — plan, build, review, run-tests, etc. Carries model, thinking level, write allowlist, and (for agent Roles) a real system prompt.

Architecture

Config/data modules, the generic interpreter, a thin chain layer, and a CLI on top. Only piwebClient.ts talks to pi-web's session API directly; piwebProject.ts talks to its Project/workspace registry.

roles.ts
The unified Role registry — agent + code, loaded from factory.config.yaml, real system prompt files resolved per agent Role.
workflowDef.ts
The Workflow YAML schema: agent/code/loop Steps, load-time validation of step-name uniqueness and loop conditions.
workflow.ts
The generic interpreter. Walks any Workflow's Steps, runs loops, threads interpolation, records every result.
tracer.ts
Writes every Workflow Run / Step / event / gate result / token count to factory.db (SQLite, WAL mode).
piwebClient.ts
The only module that talks to pi-web's session API. Starts sessions, sends prompts, waits for completion.
piwebProject.ts
Registers the target project as a pi-web Project, resolves its workspace id — what makes a real deep-link possible.
worktree.ts
Creates one git worktree + branch per Workflow Run under <project>/.pi-web-factory-worktrees/.
envelopes.ts
Zod schemas for each agent Role's required JSON output shape.
gates.ts
Verifies claims after the fact: files exist, JSON parses, tests pass, diff matches claims.
permissions.ts
Snapshots the repo before/after a turn; rolls back anything outside the allowlist.
config.ts
Shared primitives + per-project quality-gate config, read from <project>/.pi-web-factory.yaml.
run.ts
The shared agent-Step runner — parse-retry loop, permissions enforcement, token/summary capture.
chains/registry.ts
Registers every runnable Workflow by name, YAML-driven and hand-written alike, for cli.ts.
cli.ts
The command you actually type. Argument parsing, registry lookup, and I/O only.
Where this lives: jmfederico-pi-web/pi-web-factory/ in this repo — a sibling of pi-web itself, not stamped inside any target project's repo. Today it runs from a dev machine over the LAN (http://192.168.1.226:8080 — overridable via PI_WEB_FACTORY_BASE_URL); once baked into the container image (M-068, deliberately last), it'll run co-located as a sibling process, talking to pi-web over loopback.
Per-project config lives in the project, not here. <project>/.pi-web-factory.yaml declares that project's own test/typecheck/lint commands — the same repo location a future ticket-storage layer will use. pi-web-factory's own factory.config.yaml only holds the Role registry, which is shared across every project.

How a Workflow Run flows

Walking through bounded-build-review — build → loop{review, build} until approved (max 3 rounds) — since it exercises every mechanism the simpler Workflows share, plus the loop.

1

cli.ts parses your command, resolves the Workflow

--project, --workflow, an optional --session-id, and your prompt (literal text or a path to a file) get validated. An unknown project config or Workflow name fails immediately with a specific message, not a stack trace.

2

A fresh git worktree is created for this Workflow Run

worktree.ts creates <project>/.pi-web-factory-worktrees/<adwId> on a new branch, invisible to the target project's own tracked files (.git/info/exclude, not .gitignore). The project gets registered as a pi-web Project if it isn't already, and its workspace id is resolved — this is what makes a real deep-link possible later.

3

A pi-web session starts, pointed at the worktree

One real session, same kind the browser UI creates — nothing distinguishes an API-started session from a hand-started one. It gets threaded through every Step in this Workflow Run.

4

Step 1 — build (agent, medium-moe)

The task prompt is injected on the Workflow's first agent Step, prefixed with a [[pi-web-factory:role=build]] marker the before_agent_start pi extension reads to inject build's real system prompt (not prepended text — see Roles below). The repo is snapshotted before and after; anything written outside build's writes: allowlist is rolled back and the Step fails as permissions-violation.

setModelpromptwait for agent.end
↻

Loop — review → (rejected?) → build → …

review (agent, big-moe, read-only) checks the diff against the task's requirements and returns {approved: boolean, findings: [...], blocking: [...]}. If approved is false, the interpreter builds a correction message from the concrete blocking findings and re-runs build — same session, so it has the rejection's exact reasoning in context. Capped at 3 rounds; a real, distinct loop-exhausted outcome if it never converges — never silently reported as success.

up to 3 roundsreal correction message, not a generic retry
✓

Result — a 7-way discriminated outcome

success, blocked-on-human (the agent asked a question — answer it in pi-web's UI, then resume with --session-id), unparseable, permissions-violation, failed, gate-failed (a code Step's checks didn't pass), or loop-exhausted. Every branch carries the real deep-link.

How to use it

From jmfederico-pi-web/pi-web-factory/:

bun cli.ts --project /home/chris/turnstone-workspace/printer-dashboard \
  --workflow bounded-build-review \
  "Add a /health endpoint that returns 200 OK"

The prompt can also be a path to a file:

bun cli.ts --project /home/chris/turnstone-workspace/printer-dashboard \
  --workflow plan-build-review \
  ./specs/health-endpoint.md

Resume a session that got blocked waiting on a question (answer it in pi-web's UI first):

bun cli.ts --project /home/chris/turnstone-workspace/printer-dashboard \
  --workflow plan-build-review \
  --session-id 019fcb42-c0f9-73fb-881f-b80c1b232778 \
  "continue"

Exit codes

CodeMeaning
0Success.
1Failed (a Step errored outright).
2Blocked on a human — the agent asked a question mid-turn.
3Unparseable — an agent Step never produced valid JSON after retries.
4Permissions violation — a Step wrote outside its allowlist (rolled back).
5Gate failed — a code Step's checks didn't pass.
6Loop exhausted — a loop Step's until condition was never satisfied within max_rounds.
64Usage/config error — bad flags, unknown project, or unknown Workflow.

Roles & real system prompts

One Role per row, in factory.config.yaml. Agent Roles point at your box's already-seeded local-litellm provider; run-tests is a code Role — no model call, just a subprocess.

RoleKindModelWritesWhy
planagentbig-moespecs/A bad plan corrupts every Step built on it.
buildagentmedium-moeunrestricted*Mechanical given a good plan; runs most often.
reviewagentbig-moenone (read-only)Last judgment checkpoint before success or a correction round.
scoutagentmedium-moenone (read-only)Pure recon.
documentagentmedium-moedocs/, *.mdMechanical write-up of a known change.
run-testscode—noneExactly the kind of Step SSSF's philosophy says shouldn't cost a token.

* still can't touch defaults.protected_files (pi-web-factory's own machinery) — permissions.ts enforces that regardless of a Role's own writes:.

True system prompts, not prepended text. Every agent Role's prompt lives in prompts/<role>.md and is injected as a real systemPrompt by a deployed pi extension (before_agent_start hook, live in jmfederico-pi-web/plugins/pi-web-factory-prompts/) — not text glued onto the user turn. The extension identifies which Role's prompt to inject via a [[pi-web-factory:role=<name>]] marker prefixed onto that Step's first prompt, the same pattern pi-continue already uses elsewhere on this box. Confirmed byte-for-byte identical between the extension's own source of truth and pi-web-factory's copy.

The three shipped Workflows

NameShapeEnds in
plan-build-reviewplan → build → reviewan agent's judgment call, no loop
bounded-build-reviewbuild → loop{review, build} until approved, max 3 roundseither a converged review or a real loop-exhausted
plan-build-testplan → build → testa code Step (your project's real test command), the one hand-written chain kept alongside the two YAML Workflows — genuinely a different shape (a mechanical gate, not a judgment call)

All three are just entries in chains/registry.ts; plan-build-review and bounded-build-review are pure YAML data (workflows/*.yaml) run by the one generic interpreter — adding a fourth shape is a new YAML file, not new TypeScript.

Worktrees, Projects & real deep-links

Every Workflow Run gets its own git worktree under <project>/.pi-web-factory-worktrees/<adwId>, on its own pi-web-factory/<adwId> branch — concurrent runs, or a run alongside your own manual work in the project's main checkout, never collide. Worktrees are excluded from the target project's own tracked files via .git/info/exclude (not .gitignore — leaves zero footprint on the project's own committed state) and kept forever after a run finishes, favoring post-hoc inspectability over automatic cleanup at today's manual-trigger volume.

The target project is auto-registered as a real pi-web Project (idempotent — safe to call repeatedly), and its workspace id is resolved from pi-web's own git worktree list view. Every result — success or any failure branch — carries a real, working deep-link:

http://192.168.1.226:8080/?project=<id>&workspace=<id>&session=<id>

session alone does nothing in pi-web's router — project is read first. This is why deep-links weren't real in the first cut of this doc, and are now.

Connecting to pi-web's own dashboard

There's still no separate UI for pi-web-factory's own control-plane state (that's M-077, in progress) — but every session it starts is a normal pi-web session, so pi-web's own browser UI remains your dashboard for watching an agent actually work:

Open pi-web → http://192.168.1.226:8080
Every cli.ts run now prints the exact deep-link it opened, not just a bare session id — click it and you land directly on the right project/workspace/session, no manual hunting through pi-web's session list required.

LAN-only, no auth — same explicit choice as the rest of this stack. Don't expose this port past your network boundary.

Watching a run's trace (factory.db)

Independent of pi-web's UI, every Workflow Run is fully recorded in factory.db — Steps, tool calls, gate results, and (as of this session) input/output/cached token counts and an output summary per Step. Query it directly:

bun -e '
import { Database } from "bun:sqlite";
const db = new Database("factory.db", { readonly: true });
console.log(db.query(
  "select name, status, seq, kind, input_tokens, output_tokens, output_summary " +
  "from phases where adw_id=? order by seq"
).all("adw_xxxxxxxxxxxx"));
'

A real-time Gantt-style visualizer on top of this data — one card per Workflow Run, idle time collapsed, the currently-active Step highlighted live — is the next planned piece (M-077). For now, direct SQL is the tool.

M-072 hit a real architectural fork rather than a routing detail: the pi-web container that hosts every live session doesn't have pi-web-factory on its filesystem yet (expected — that's M-068's job, and M-068 is deliberately last), so a Skill's bash tool has no path to cli.ts today. The two live options both carry enough risk or novelty (restarting the interactive pi-web container itself vs. an untested per-invocation disposable-container pattern) to warrant a real decision rather than a unilateral pick — see the card for both options in full.

There's also a durable ticket layer sketched but not built: a trimmed .fleet-style backlog/ → now/ → done/ queue that would let you author work items and have them picked up later, rather than every run being manually triggered. cli.ts's --project/--workflow/prompt/--session-id shape was deliberately designed to be that queue's eventual calling convention, unchanged by this session's redesign.
