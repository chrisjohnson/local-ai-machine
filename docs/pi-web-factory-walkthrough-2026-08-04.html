pi-web-factory

A deterministic control plane for AI coding agents, built on top of your existing jmfederico-pi-web stack. This page is a guided walkthrough of what got built this session (cards M-061 through M-067), how it works, and how to drive it yourself.

What is this?

pi-web-factory brings the SSSF pattern — deterministic code owns sequencing, retries, and acceptance; an AI agent works inside one bounded, typed phase at a time — to your running pi-web deployment. Instead of spawning a bare pi CLI subprocess (which doesn't exist on PATH anywhere in the jmfederico-pi-web container), it drives real pi-web sessions over the same HTTP/WebSocket API your browser uses.

The practical upshot: every session pi-web-factory starts is a completely ordinary pi-web session. It shows up in the browser UI exactly like one you started by hand. You can watch an agent work in real time, and if something needs a human, you can even answer it there — something the upstream SSSF tool can't do at all, since it has no equivalent UI.

Why it exists

Prompting a coding agent once and hoping is fine for a one-off. It stops being fine the moment you want the same request to work the same way every time — with retries that don't throw away context, a record of what each phase actually did, and a hard boundary on what a phase is allowed to touch. That's what this adds on top of pi-web:

  • Typed output, every time. An agent's only real output is one JSON object matching a schema declared up front. If it doesn't parse, the harness re-prompts the same session with a correction naming exactly what was wrong — never a cold restart.
  • Enforced write boundaries. Every agent identity has a writes: allowlist. Anything it touches outside that allowlist gets rolled back automatically, and — importantly — the phase is reported as failed, not silently patched up.
  • A full trace. Every phase, every tool call, every gate result lands in a local SQLite db (factory.db) as it happens, queryable independently of pi-web's own session history.
  • One shared control plane, many projects. Unlike upstream SSSF (one install per repo), pi-web-factory is one install that can target any project by absolute path.

Architecture

Seven small modules, each independently tested, plus a thin chain layer and a CLI on top. Only one of them — piwebClient.ts — actually talks to pi-web.

tracer.ts
Writes every phase/event/gate result to factory.db (SQLite, WAL mode).
piwebClient.ts
The only module that talks to pi-web. Starts sessions, sends prompts, waits for completion.
envelopes.ts
Zod schemas for each agent identity's required JSON output shape.
gates.ts
Verifies claims after the fact: files exist, JSON parses, tests pass, diff matches claims.
permissions.ts
Snapshots the repo before/after a turn; rolls back anything outside the allowlist.
config.ts
Loads factory.config.yaml: the agent roster and per-project settings.
run.ts
The shared phase-runner every chain calls — wires all of the above together.
chains/planBuildTest.ts
The first real chain: plan → build → test.
cli.ts
The command you actually type. Argument parsing and I/O only.
Where this lives: jmfederico-pi-web/pi-web-factory/ in this repo — a sibling of pi-web itself, not stamped inside any target project's repo. Today it runs from a dev machine over the network (http://192.168.1.21:8080); once baked into the container image (M-068, not yet done), it'll run co-located as a sibling process, talking to pi-web over loopback.

How work flows through it

This is what actually happens, step by step, when you run the plan-build-test chain against a project — the exact sequence chains/planBuildTest.ts and modules/run.ts execute together.

1

cli.ts parses your command and loads the roster

--project, --chain, an optional --session-id, and your prompt (literal text or a path to a file) get validated. factory.config.yaml loads; an unknown project or chain name fails immediately with a specific message, not a stack trace.

2

A pi-web session starts (or an existing one resumes)

One real session against your target project's working directory. This is the exact same kind of session the browser UI creates — nothing distinguishes an API-started session from a hand-started one.

3

Phase 1 — plan

The plan agent (big-moe, high thinking) gets the task and a required JSON schema. The repo is snapshotted before the prompt is sent.

setModelpromptwait for agent.end
?

Did it parse?

If the response isn't valid JSON matching the schema, the harness re-prompts the same session with a correction naming exactly what was wrong — up to 3 attempts before the phase fails as unparseable. In live testing, both agents got it right on the first try every time — but the retry path is real and covered by its own tests.

retry ≤ 3×
4

Permissions are enforced

The repo is diffed against the pre-prompt snapshot. Anything outside the agent's writes: allowlist is rolled back — tracked-file edits via git checkout --, new untracked files by deletion. If anything was unauthorized, the phase is marked permissions-violation and the chain stops — even though the rollback itself succeeded. A violation always fails the phase; that's not optional.

any violation → phase fails
5

Phase 2 — build, same session

The build agent (medium-moe) continues the same pi-web session — not a fresh one — with the plan's summary in context, and actually writes files using its real tools. Same parse-retry and permissions-enforcement steps apply.

6

Phase 3 — test, no agent involved

A plain code phase: your project's configured test command runs as a subprocess. No model call — this is exactly the kind of step SSSF's own philosophy says shouldn't cost a token.

✓

Result

One of five outcomes, always carrying the adwId/sessionId so you can always find the run again: success, blocked-on-human (the agent asked a question — go answer it in pi-web's UI, then resume with --session-id), unparseable, permissions-violation, or failed.

How to use it

From jmfederico-pi-web/pi-web-factory/:

bun cli.ts --project /home/chris/turnstone-workspace/printer-dashboard \
  --chain plan-build-test \
  "Add a /health endpoint that returns 200 OK"

The prompt can also be a path to a file:

bun cli.ts --project /home/chris/turnstone-workspace/printer-dashboard \
  --chain plan-build-test \
  ./specs/health-endpoint.md

Resume a session that got blocked waiting on a question (answer it in pi-web's UI first):

bun cli.ts --project /home/chris/turnstone-workspace/printer-dashboard \
  --chain plan-build-test \
  --session-id 019fcb42-c0f9-73fb-881f-b80c1b232778 \
  "continue"

Exit codes

CodeMeaning
0Success — plan, build, and test all passed.
1Failed (e.g. the test command failed).
2Blocked on a human — the agent asked a question mid-turn.
3Unparseable — the agent never produced valid JSON after 3 attempts.
4Permissions violation — the agent wrote outside its allowlist (rolled back).
64Usage/config error — bad flags, unknown project, or unknown chain.

The roster — factory.config.yaml

One agent identity per row. Models point at your box's already-seeded local-litellm provider — big-moe and medium-moe are live model roles today, not placeholders.

AgentModelWritesWhy
planbig-moespecs/A bad plan corrupts every phase built on it.
buildmedium-moeunrestricted*Mechanical given a good plan; runs most often.
reviewbig-moenone (read-only)Last judgment checkpoint before success.
scoutmedium-moenone (read-only)Pure recon.
documentmedium-moedocs/, *.mdMechanical write-up of a known change.

* still can't touch defaults.protected_files (pi-web-factory's own machinery) — permissions.ts enforces that regardless of an agent's own writes:.

Per-project quality commands live in the same file's projects: map, keyed by absolute path — this is what the test phase runs.

Connecting to pi-web's own dashboard

There's no separate UI for pi-web-factory itself (yet) — and honestly, you may not need one. Every session it starts is a normal pi-web session, so pi-web's own browser UI is your dashboard:

Open pi-web → http://192.168.1.21:8080
Print the sessionId from your cli.ts run (it's shown immediately, before the chain even finishes) and find it in pi-web's session list on the LAN. You can watch tokens stream in live, exactly as if you'd started the session by hand — because you didn't do anything pi-web itself would treat differently.

LAN-only, no auth — same explicit choice as the rest of this stack. Don't expose this port past your network boundary.

Watching a run's trace (factory.db)

Independent of pi-web's UI, every run is fully recorded in factory.db — phases, tool calls, gate results, costs. Query it directly:

bun -e '
import { Database } from "bun:sqlite";
const db = new Database("factory.db", { readonly: true });
console.log(db.query(
  "select name, status, seq from phases where adw_id=? order by seq"
).all("adw_xxxxxxxxxxxx"));
'

There's no visualizer for this yet — that's an explicitly deferred piece of the design (see the design doc's §3.5). For now, direct SQL is the tool.

Today, pi-web-factory runs from a dev machine over the network. M-068 is what makes it a real, always-available part of the stack — baked into the jmfederico-pi-web image itself, the same way the pi-continue-companion plugin already is. M-069 (giving each agent identity a true system prompt instead of text prepended to the first message) is deliberately parked pending a go/no-go decision — the interim workaround already works, this is a fidelity improvement, not a blocker.

There's also a durable ticket layer sketched but not built: a trimmed .fleet-style backlog/ → now/ → done/ queue that would let you author work items and have them picked up later, rather than every run being manually triggered. cli.ts's argument shape was deliberately designed to be that queue's eventual calling convention, unchanged.
