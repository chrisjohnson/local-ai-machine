Biggest findings

  • Small active-param-count MoE models dominate this memory-bandwidth-bound hardware — the single most consistent pattern across every engine tested. GLM-4.7-Flash (~3B active) hit the fastest llama.cpp generation speed measured anywhere in this project (70.1 tok/s); Gemma-4-26B-A4B-it (~4B active) was the fastest vLLM model tested (50.38 tok/s c8) and scored a perfect coding result; GPT-OSS-20B (~3.6B active) posted the best c8 throughput of the coding-comparison lineup (56.72 tok/s) and the best concurrency headroom (30.02×) of any model tested. Dense models of similar or smaller total size (Qwen3.6-27B, Gemma-4-31B-it) trail badly on every engine.
  • llama.cpp direct beats Ollama substantially — and far more so for MoE models than dense ones. On the identical GGUF file, GLM-4.7-Flash is ~5.4× faster on llama.cpp direct than Ollama (70.1 vs ~13 tok/s); Qwen3.6-35B-A3B (MoE) is ~5.7× faster (63.43 vs 11.18 tok/s). But Qwen3.6-27B, a dense model, shows only a ~17% gap (12.75 vs 10.59 tok/s) between the same two engines. Only 3 data points (2 MoE + 1 dense), not a controlled ablation, but a real and repeated pattern worth flagging.
  • GPT-OSS-20B has the best recorded concurrency headroom of any model tested — 30.02× max concurrency at 131072 context (95.81 GiB of KV cache from a 14.16 GiB weights footprint), edging out GLM-4.7-Flash-AWQ's previous-best 28.10×. Its sibling GPT-OSS-120B, by contrast, is the slowest c1 throughput (8.46 tok/s) of any small-active-param MoE model tested — a real, unexplained (hypothesized but unconfirmed) per-model MXFP4 kernel-path effect, not a blanket format penalty, since GPT-OSS-20B uses the identical format and performs normally.
  • The llama-server concurrent-serving experiment shows a real ~3× aggregate throughput gain over single-stream llama.cpp — Qwen3.6-27B via llama-server -np 4 -cb -kvu sustained ~38.3-39.1 tok/s aggregate at concurrency 4 vs 12.60 tok/s at concurrency 1, at the cost of ~27% longer per-request wall-clock time. This is the first concurrent-serving (not just single-stream llama-bench) number ever measured for llama.cpp on this hardware, and a correctness check (4 concurrent distinguishable prompts) passed cleanly first, given two known open upstream concurrency bugs on adjacent backends.
  • A recurring `judge_incorrect` (Tier J) failure shows up in every model that's had the six-tier harness run against it — GLM-4.7-Flash-AWQ, GPT-OSS-120B, and GPT-OSS-20B all failed this exact same subtly-buggy-palindrome-check task, and the production primary (Qwen3.6-35B-A3B) failed an equivalent spot-check too. This is a real, cross-model finding — none of the models tested so far are reliable LLM-judges without more scrutiny — not a fluke of one model.
  • The current production primary (Qwen3.6-35B-A3B) is not the strongest coding performer on any tier tested — four models (80B GPTQ, 122B AWQ, Gemma-4-31B, Gemma-4-26B-A4B) hit a perfect 5/5 on the original Tier A/B harness, while the primary landed at 4/5, and GPT-OSS-120B posted the best six-tier score recorded (11/12).
  • Quantization can beat a smaller model's raw footprint — the 80B-total Qwen3-Coder-Next-GPTQ-4bit is smaller on disk (46.49 GiB) than the 35B-total bf16 primary (66.97 GiB), despite having 2.3× the parameters. Model size alone is a poor proxy for memory footprint once quantization enters the picture.
  • Speed and coding capability do not correlate. Gemma-4-31B-it was the slowest model tested via vLLM (3.23/11.73 tok/s c1/c8) yet scored a perfect 5/5 on the coding harness — the single starkest speed/capability mismatch recorded.

Data quality — an honest accounting

Single-sample vs. averaged measurements

  • vLLM numbers are the most rigorous in this project — every c1/c8 figure comes from vllm bench serve against a fixed random dataset (20 prompts @ c1, 100 prompts @ c8), a real load-generation tool, not a single manual request. Still single-run-per-configuration, not multi-trial-averaged (matching this project's established no-repeated-trials convention).
  • llama.cpp direct's llama-bench numbers are averaged across internal repeated iterations (the ± figures, e.g. 342.55 ± 14.41) — this is the tool's own built-in repeat-and-average behavior, the closest thing to statistical rigor in this project's speed data.
  • Ollama's numbers are single real-generation samples, not averaged benchmark runs. Every Ollama tok/s figure in this dashboard is derived from one /api/generate request's eval_count/eval_duration fields — reasoning-mode <think> traces inflate the token count in ways a dedicated benchmark tool would isolate. Treat Ollama-vs-other-engine ratios as directionally comparable, not precise.
  • Several numbers exist only as narrative prose in OPTIMIZATIONS.md or an older HTML report, not as a saved results/ file — flagged inline throughout this dashboard with a "no results file" pill. This includes: GLM-4.7-Flash-AWQ's vLLM c1/c8 speed numbers, GLM-4.7-Flash's llama.cpp and Ollama numbers, Gemma-4-26B-A4B-it's llama.cpp numbers, and the 122B AWQ non-eager re-test. These are real measurements per this project's own documentation discipline, just not yet migrated to the newer results/<slug>--<engine>.txt convention adopted partway through the project.
  • The llama-server concurrent-serving benchmark is a hand-rolled concurrent-curl load test, not vllm bench serve-style tooling (that tool only targets vLLM) — a single run per concurrency level (c1, c4), cross-checked against llama.cpp's own per-request timings block and server-side print_timing log lines, but not a repeated-trial average.

Engines / models still untested or broken

  • Gemma-4-26B-A4B-it cannot run on Ollama at all on the current pinned version (0.17.7) — unknown model architecture: 'gemma4'. This is a genuine architecture-support gap in that specific Ollama build, not a config or download problem; a newer Ollama release almost certainly supports it (per later research in OPTIMIZATIONS.md, gemma4 support landed in Ollama v0.21.0), but upgrading was deliberately deferred pending a broader Ollama-version review.
  • MTP (multi-token-prediction) speculative decoding could not be benchmarked for Qwen3.6-27B — the locally-downloaded plain GGUF doesn't ship MTP head tensors; a separate unsloth/Qwen3.6-27B-MTP-GGUF repo would be needed, and no new download was made per this session's standing check-in rule. The mechanism itself is confirmed real and correctly wired in the toolbox build (matches the upstream PR author's own invocation) — this is a missing-artifact gap, not a broken feature.
  • North-Mini-Code-1.0-w4a16, GPT-OSS-120B llama.cpp GGUF repack, Qwen3.5-122B-A10B GGUF, NVIDIA-Nemotron-3-Super-120B-A12B, and MiniMax-M2.7 are all UNTESTED-BUT-DOWNLOADED (or not yet downloaded) on this machine — reference numbers exist only from kyuz0's own external upstream results.json for the llama.cpp candidates, not reproduced locally.
  • Six of ten coding-capability entries in this dashboard only have the original 5-task Tier A/B harness result — only GLM-4.7-Flash-AWQ, GPT-OSS-120B, and GPT-OSS-20B have been run through the newer six-tier harness (Tier J/P/D/Q). Direct overall-score comparison across the two harness generations should be read as directional, not a precise apples-to-apples ranking, since the newer harness is strictly harder (more tasks, more failure surface).
  • Qwen2.5-VL-7B-Instruct has no coding-harness or footprint data at all — deliberately excluded as a vision/OCR specialist, not a coding candidate.

Known methodology caveats worth remembering

  • GPT-OSS's harmony chat format requires a different vllm bench serve invocation than every other model in this project. The standard --backend openai-chat --endpoint /v1/chat/completions --ignore-eos recipe fails 100% of the time against GPT-OSS-120B/20B (openai_harmony.HarmonyError: Unexpected token 200002...) because forcing generation past the model's natural stop token violates harmony's token grammar. Fix used: --backend openai --endpoint /v1/completions (bypasses the chat template/harmony parser). Confirmed via manual curl before trusting the benchmark tool's numbers — a genuine, necessary methodology deviation for this model family, not a silent substitution.
  • Ollama's MoE-vs-dense overhead gap is only a 2-MoE / 1-dense sample — GLM-4.7-Flash (~5.4×) and Qwen3.6-35B-A3B (~5.7×) both show a large llama.cpp-vs-Ollama gap, while Qwen3.6-27B (dense, ~17%) shows a much smaller one. A real, repeated pattern worth flagging prominently (see Biggest Findings above), but not a controlled ablation — the mechanism (MoE routing overhead interacting with Ollama's Go scheduler) is a hypothesis, not confirmed.
  • GPT-OSS-120B's unusually slow c1 throughput (8.46 tok/s) has an unconfirmed root-cause hypothesis — plausibly this vLLM build's MXFP4 MoE kernel path (MoEPrepareAndFinalizeNoDPEPMonolithic) not being a fully optimized low-bit matmul on gfx1151 (no native FP4 matrix-core hardware on RDNA3.5). Not confirmed via kernel profiling. The sibling GPT-OSS-20B performs normally for its size class using the identical format, which argues against a blanket "MXFP4 is slow here" explanation and toward something specific to the 120B tier's much larger expert pool.
  • Background download-queue contention measurably affects prompt-processing (PP) speed but not generation (TG) speed on llama.cpp direct — a contaminated Gemma-4-26B-A4B-it run showed pp512 1192.75 vs a clean run's 1251.33 (~4.9% hit), while tg128 was statistically unaffected (54.50 vs 53.96, within run-to-run noise). PP-sensitive benchmarks should pause the download queue first; TG-only comparisons are more robust to background contention.
  • The 5-task Tier A/B harness underwent 6 real bugfixes during development (documented in benchmark-report-2026-07-23.html) — most relevantly, a fallback for extracting code from a model's reasoning trace when the final-answer field comes back empty. The production primary's 4/5 score predates this fix and is likely a conservative floor, not a fully comparable number against the other Tier A/B results in this dashboard's coding table.
  • The llama-server concurrent-serving correctness check was run deliberately before any throughput number was trusted, given two real open upstream bugs: a HIP/ROCm-specific cross-request corruption bug (ggml-org/llama.cpp#25992, still open) and an older, unresolved (auto-closed-stale, never actually fixed) RADV concurrent-slot-hang report (#20906) on the same Vulkan/RADV backend this project uses. The check passed cleanly (4 distinguishable concurrent prompts, all correct, no cross-contamination) before any tok/s number was measured.
